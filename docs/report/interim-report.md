**Progressive Multi-Agent Collaboration for Database Fault Diagnosis**

## Abstract

Multi-agent systems for database fault diagnosis may invoke multiple specialist agents for each request, increasing token usage and latency, while a single agent may struggle to diagnose compound faults. This study proposes a progressive collaboration approach in which a single agent performs the initial diagnosis and additional specialist agents are invoked only when the available evidence is insufficient to determine the root cause. As an initial step, we implemented a diagnosis service with three read-only diagnostic tools and established a single-agent baseline using a reproduced missing-index fault. Across 30 fault trials and 10 normal trials, the single agent correctly diagnosed all cases. Fault diagnosis required an average of 5,710 input tokens and 10.4 seconds per trial. These results provide a baseline for evaluating the accuracy, token usage, and latency of different collaboration structures under compound-fault conditions.

웹 서비스의 API 응답 지연은 애플리케이션 코드, 데이터베이스 커넥션 풀, SQL 쿼리, 실행 계획, 락 등 다양한 원인으로 발생합니다. 운영자는 응답시간 지표를 확인한 뒤 실행된 SQL과 실행 계획 등을 단계적으로 분석하여 원인을 좁혀 가게됩니다. 최근에는 이러한 진단 과정을 대규모 언어 모델(LLM) 기반 에이전트로 자동화하려는 연구가 진행되고 있습니다.

에이전트 기반 진단 구조는 크게 단일 에이전트 구조와 멀티에이전트 구조로 구분할 수 있습니다. 단일 에이전트 구조는 하나의 에이전트가 모든 진단 도구를 사용하며, 멀티에이전트 구조는 분석 영역별로 전문 에이전트를 배치합니다. 멀티에이전트 구조에서 여러 전문 에이전트를 매 요청마다 호출하면 토큰 사용량과 진단 시간이 증가할 수 있습니다. 반면 단일 에이전트 구조는 진단 맥락을 하나의 에이전트에서 관리할 수 있지만, 여러 원인이 복합적으로 작용하는 장애에서는 진단 정확도가 낮아질 가능성이 있습니다.

기존 연구에서도 멀티에이전트 시스템의 실행 비용을 줄이기 위한 접근이 제안되었습니다. Anthropic[1]은 2026년 10월 발표한 여러 기업의 적용 사례에서 도구를 사용하는 단일 에이전트가 다중 서브에이전트 구조보다 높은 품질과 낮은 비용 및 지연시간을 보인 경우를 소개했습니다. 하지만 독립적인 작업을 병렬로 처리해야 하거나 컨텍스트가 지나치게 커지는 상황에서는 서브에이전트가 효과적일 수 있다고 설명했습니다.

본 연구에서는 단일 에이전트가 먼저 장애를 진단하고, 현재 확보한 증거만으로 원인을 확정하기 어려운 경우에만 전문 에이전트를 추가로 호출하는 점진적 협력 구조를 제안합니다. 이를 통해 다음 연구 질문을 검증하고자 합니다.

**점진적 협력 구조는 단일 에이전트 구조보다 높은 진단 정확도를 달성하면서, 전면 협력 구조보다 적은 토큰을 사용할 수 있는가?**

본 보고서에서는 연구의 첫 단계로 세 가지 협력 구조를 동일한 조건에서 비교하기 위한 진단 서비스를 설계하고 구현했습니다. 또한 인덱스 미사용 장애를 재현한 환경에서 단일 에이전트 구조의 기준선을 측정했습니다.

## Ⅱ. 본론

### 1. 점진적 협력 구조

제안하는 점진적 협력 구조는 다음 세 단계로 동작합니다.

1. **초기 진단:** 주 에이전트가 요청 정보와 관측 데이터를 분석하여 초기 원인 후보를 도출합니다.
2. **점진적 호출:** 현재 확보한 증거만으로 원인을 확정하기 어려우면 추가 분석에 필요한 전문 에이전트를 하나씩 호출합니다.
3. **종료 판단:** 진단 확신도가 설정한 기준을 충족하면 추가 협력을 종료하고 최종 원인과 권장 조치를 반환합니다.

다음에 호출할 전문 에이전트는 효용 함수를 기준으로 선택합니다. 전문 에이전트 (a_i)의 효용은 다음과 같이 정의합니다.

[
U(a_i)=\Delta Q(a_i)-\alpha C(a_i)-\beta L(a_i)
]

여기서 (\Delta Q)는 예상 진단 정확도 향상, (C)는 예상 토큰 사용량, (L)은 예상 추가 지연시간을 의미합니다. (\alpha)와 (\beta)는 각각 토큰 사용량과 지연시간에 대한 가중치입니다. 효용이 설정한 기준을 초과하는 전문 에이전트만 추가로 호출합니다.

연구에서는 다음 세 가지 협력 구조를 비교합니다.

- **단일 에이전트 구조:** 하나의 에이전트가 모든 진단 도구를 사용하여 처음부터 끝까지 진단합니다.
- **전면 협력 구조:** 모든 진단 요청에서 다섯 개의 전문 에이전트를 호출합니다.
- **점진적 협력 구조:** 현재 진단 결과를 바탕으로 추가 분석에 필요한 전문 에이전트만 선택적으로 호출합니다.

### 2. 진단 서비스 설계

진단 서비스는 사용자가 응답이 느린 API의 HTTP 메서드와 경로를 전달하면 원인을 분석하여 진단 결과를 반환합니다.

진단 대상인 주문 서비스와 진단 서비스는 별도 프로세스로 실행합니다. 실제 운영 서비스에는 자체 진단 API가 없다는 점을 고려하여 실험 환경에서도 두 서비스를 분리했습니다. 두 서비스는 Spring Boot로 구현했으며, 데이터베이스는 MySQL 8.4를 사용합니다.

에이전트는 다음 세 가지 진단 도구를 통해 관측 데이터를 수집합니다.

| 도구        | 데이터 출처                              | 반환값                                                    |

| 응답시간 조회   | Spring Boot Actuator의 HTTP 요청 지표    | 호출 횟수, 평균, 최대, p50, p95, p99 응답시간                      |

| 실행 계획 조회  | 문장 요약 테이블에 저장된 예시 SQL               | 예시 SQL, 실행 계획                                          |

진단 도구는 운영 환경에서의 안전성을 고려하여 다음 세 가지 원칙에 따라 설계했습니다.

1. **실행 계획 조회 도구는 SQL 문자열 대신 문장 식별자를 입력받습니다.**&#x20;
2. **실행 계획은 진단 대상 SQL을 실제로 실행하지 않는 방식으로 조회합니다.**&#x20;
3. **진단 서비스는 읽기 전용 계정으로 데이터베이스에 접속합니다.**

진단 결과는 원인 범주, 대상 테이블, 대상 컬럼, 판단 근거, 권장 조치의 다섯 가지 필드로 구성된 구조화 출력으로 제공 받습니다. 원인 범주는 연구 계획에서 정의한 다섯 가지 장애 시나리오에 `NO_PROBLEM`과 `UNDETERMINED`를 추가한 총 일곱 가지입니다. 각각 정상 상태와 진단 근거가 부족한 상태를 구분하기 위한 값입니다.

진단 결과의 형식을 고정하여 별도의 수동 판정 없이 스크립트로 성공 여부를 채점할 수 있도록 했습니다.

협력 구조와 진단 도구는 각각 인터페이스로 분리했습니다. 이를 통해 전면 협력 구조와 점진적 협력 구조를 구현하거나 커넥션 분석 및 락 분석 도구를 추가할 때 기존 호출부를 변경하지 않고 구현체를 확장할 수 있습니다.

모델 요청과 도구 호출을 반복하는 실행 로직은 세 가지 협력 구조가 공통으로 사용하는 클래스로 구현했습니다. 해당 클래스에서는 요청별 토큰 사용량을 집계하고 도구 호출 순서를 기록합니다.

## Ⅲ. 실험

### 1. 실험 환경

주문 서비스의 `orders` 테이블에 500만 행을 적재했으며, 고객 한 명당 주문은 약 10건으로 구성했습니다. 인덱스 미사용 장애는 조회 조건에 사용하는 `customer_id` 컬럼의 인덱스를 삭제하여 재현했습니다.

인덱스 적용 상태에서 주문 조회 API의 p99 응답시간은 0.040초였습니다. 인덱스를 제거한 후에는 단일 요청의 평균 응답시간이 1.358초, 동시 요청 수 2인 조건에서 p99 응답시간이 2.723초로 증가했습니다. 이때 실행 계획에서는 `Table scan on orders`가 확인되었습니다.

실행 SQL은 MySQL Performance Schema의 문장 요약 테이블[2]에서 조회하고, 실행 계획은 `EXPLAIN`[3]으로 확인했습니다.

실험 모델은 Claude Opus 5.5이며, effort는 기본값인 `medium`으로 설정했습니다. 시스템 프롬프트에는 p99 응답시간이 500ms를 초과하면 응답 지연으로 판단한다는 기준만 명시했습니다. 도구 호출 순서는 지정하지 않았으며, 에이전트가 자율적으로 선택한 호출 순서를 기록했습니다.

### 2. 측정 절차

각 측정 회차는 다음 다섯 단계로 진행했습니다.

1. 주문 서비스를 재기동하여 Actuator 지표를 초기화했습니다.
2. 데이터베이스의 실행 통계를 초기화했습니다.
3. 동시 요청 수 2로 주문 조회 API를 총 40회 호출했습니다.
4. 진단 서비스에 진단을 요청했습니다.
5. 진단 결과와 실행 통계를 기록했습니다.

회차마다 주문 서비스를 재기동하고 실행 통계를 초기화하여 이전 회차의 관측 데이터가 다음 회차에 영향을 주지 않도록 했습니다.

인덱스를 제거한 장애 주입 조건에서 30회, 인덱스가 적용된 정상 조건에서 10회를 측정했습니다. 정상 조건은 문제가 없는 API를 장애로 잘못 판단하는지 확인하기 위한 대조군으로 설정했습니다.

채점 기준은 다음과 같습니다.

- **장애 주입 조건:** 원인 범주가 `MISSING_INDEX`이고, 대상이 `orders` 테이블의 `customer_id` 컬럼이면 성공으로 판정했습니다.
- **정상 조건:** 원인 범주가 `NO_PROBLEM`이면 성공으로 판정했습니다.

측정은 2026년 11월 13일에 수행했습니다. 측정 중 모델 API가 일시적으로 응답하지 않아 네 번의 시도가 실패했으며, API 복구 후 해당 회차를 첫 단계부터 다시 실행했습니다.

실험 결과에서 확인한 주요 사항은 다음 세 가지입니다.

첫째, **단일 에이전트는 총 40회 모두 올바르게 진단했습니다.** 장애 주입 조건에서는 30회 중 30회, 정상 조건에서는 10회 중 10회 성공했습니다. 정확 이항 신뢰구간을 적용하면 95% 신뢰수준에서 실제 성공률의 하한은 장애 주입 조건에서 약 88.4%, 정상 조건에서 약 69.2%입니다.

둘째, **동일한 조건에서는 모든 회차에서 도구 호출 순서가 일치했습니다.** 장애 주입 조건의 30회에서는 응답시간 조회, 실행 SQL 조회, 실행 계획 조회 순서로 호출했습니다. 정상 조건의 10회에서는 응답시간 조회와 실행 SQL 조회만 호출했습니다. 입력 토큰 수 역시 각 조건 내에서 회차별 차이가 없었습니다.

셋째, **정상 조건에서도 실행 SQL 조회 도구가 호출되었습니다.** 정상 조건에서는 회차당 모델 요청이 2회이고 도구 호출이 2회였습니다. 이는 첫 번째 모델 응답에서 두 도구를 함께 요청했을 가능성을 보여줍니다. 응답시간 지표만으로 정상 여부를 판단할 수 있는 경우에는 실행 SQL 조회를 생략하여 토큰 사용량과 진단 시간을 줄일 여지가 있습니다.

전체 40회 측정에서 사용한 토큰은 입력 206,150개, 출력 20,986개입니다.

### 4. 실험의 한계

이번 실험에는 다음 세 가지 한계가 있습니다.

첫째, 인덱스 미사용 장애 한 가지만 재현했으며, 복합 장애는 포함하지 않았습니다. 따라서 여러 원인이 동시에 발생하는 상황에서의 진단 성능은 확인하지 못했습니다.

둘째, 진단 도구가 세 개로 제한되어 있어 단일 에이전트가 처리해야 하는 분석 범위가 비교적 좁았습니다. 이번 조건에서는 단일 에이전트의 진단 실패 사례를 관찰하지 못했습니다.

셋째, 측정 횟수는 장애 주입 조건 30회와 정상 조건 10회로 설정했으며, 표본 수를 통계적 검정력에 따라 산정하지 않았습니다. 또한 회차당 API 호출 수가 40회이므로 p99 응답시간은 제한된 표본을 기반으로 추정되었습니다.

## Ⅳ. 결론 및 향후 연구 방향

본 보고서에서는 점진적 멀티에이전트 협력 구조의 효과를 검증하기 위한 진단 서비스를 설계하고 구현했으며, 인덱스 미사용 장애를 대상으로 단일 에이전트 구조의 기준선을 측정했습니다.

단일 에이전트는 장애 주입 조건 30회와 정상 조건 10회에서 모두 올바른 진단 결과를 반환했습니다. 장애 한 건을 진단하는 데 평균 5,710개의 입력 토큰과 10.4초가 소요되었습니다.

이는 이번에 재현한 인덱스 미사용 장애에서는 단일 에이전트만으로도 정확한 진단이 가능했음을 보여줍니다. 따라서 향후 연구에서는 단일 에이전트의 진단 정확도가 낮아지는 조건을 확인하고, 전문 에이전트와의 협력이 정확도와 실행 비용에 미치는 영향을 검증해야 합니다.

향후 연구는 다음 세 단계로 진행합니다.

1. **장애 시나리오 확장:** 나머지 네 가지 장애 시나리오를 재현하고, 두 가지 원인이 동시에 발생하는 복합 장애를 구성합니다. 이를 통해 단일 에이전트 구조의 진단 실패 조건을 확인합니다.
2. **협력 구조 구현 및 비교:** 다섯 개의 전문 에이전트와 전면 협력 구조, 점진적 협력 구조를 구현합니다. 기존에 분리한 협력 구조 인터페이스를 활용하여 동일한 측정 절차와 채점 기준으로 비교합니다.
3. **효용 함수 구체화:** 전문 에이전트 호출에 따른 예상 정확도 향상, 토큰 사용량, 추가 지연시간을 추정하는 방법을 정의합니다. 이번 실험에서 기록한 도구 호출 순서와 토큰 사용량을 초기 분석 자료로 활용합니다.

최종적으로 단일 에이전트, 전면 협력, 점진적 협력 구조의 진단 정확도와 토큰 사용량, 진단 시간을 비교하여 점진적 협력 구조의 효과를 검증할 계획입니다.
