# 데이터베이스 장애 진단을 위한 점진적 멀티에이전트 협력 구조

**Progressive Multi-Agent Collaboration for Database Fault Diagnosis**

## Abstract

Multi-agent systems for database fault diagnosis may invoke all specialist agents for every diagnostic request, resulting in increased token consumption and latency. This study proposes a progressive collaboration architecture that invokes specialist agents one at a time, selects the next agent using a utility function, and terminates the diagnostic process when sufficient confidence is reached. We implemented a diagnostic service comprising five read-only diagnostic tools and five specialist agents. Four architectures were evaluated across three reproduced fault scenarios and one normal condition, with 40 trials per architecture. All four architectures correctly diagnosed every trial. Compared with full collaboration, progressive collaboration reduced input token consumption by 57% and diagnostic latency by 43%. It also consumed 39% fewer input tokens than fixed-order collaboration. However, the single-agent architecture remained the most cost-efficient approach for the single-cause faults evaluated in this study.

## Ⅰ. 서론

웹 서비스의 API 응답 지연은 애플리케이션 코드, 데이터베이스 커넥션 풀, SQL 쿼리, 실행 계획, 락과 같은 여러 영역에서 발생할 수 있습니다. 운영자는 API 응답시간 지표를 확인하고, 실행된 SQL과 실행 계획을 단계적으로 분석하여 지연 원인을 좁혀 나갑니다. 최근에는 이러한 장애 진단 과정을 대규모 언어 모델(LLM) 기반 에이전트로 자동화하기 위한 연구가 진행되고 있습니다.

에이전트 기반 장애 진단 구조는 단일 에이전트 구조와 멀티에이전트 구조로 구분할 수 있습니다. 단일 에이전트 구조에서는 하나의 에이전트가 모든 진단 도구를 사용하며, 멀티에이전트 구조에서는 분석 영역별로 전문 에이전트를 구성합니다. 다만 모든 진단 요청에서 전문 에이전트를 호출하면 토큰 사용량과 진단 시간이 증가한다는 문제가 있습니다.

Anthropic[1]은 2026년 10월 여러 기업의 적용 사례를 비교하여, 스킬을 활용하는 단일 에이전트가 서브에이전트 구조보다 더 나은 결과를 보이는 경우가 많았다고 설명했습니다. 반면 컨텍스트의 크기가 지나치게 커지는 경우, 여러 작업을 병렬로 처리해야 하는 경우, 단일 에이전트가 적절한 도구를 선택하지 못하는 경우에는 서브에이전트 구조가 여전히 효과적이라고 설명합니다. 따라서 분석 영역별로 전문 에이전트를 분리하는 방식은 특정 상황에서 유용하지만, 그에 따른 비용도 함께 고려해야 합니다.

본 연구에서는 전문 에이전트를 한 번에 하나씩 호출하고, 효용 함수를 통해 다음에 호출할 전문 에이전트를 선택하며, 진단 결과의 확신도가 일정 기준에 도달하면 추가 호출을 중단하는 점진적 협력 구조를 제안합니다. 이를 통해 다음 연구 질문을 검증하고자 합니다.

**점진적 협력 구조는 단일 에이전트 구조보다 높은 진단 정확도를 달성하면서 전면 협력 구조보다 적은 토큰을 사용할 수 있는가?**

본 보고서에서는 이를 검증하기 위해 장애 진단 서비스를 설계하고 구현했으며, 세 가지 장애 시나리오와 정상 조건에서 네 가지 에이전트 구조를 동일한 실험 절차에 따라 비교한 결과를 제시합니다.

## Ⅱ. 본론

### 1. 점진적 협력 구조

본 연구에서 제안하는 점진적 협력 구조는 다음 세 단계로 동작합니다.

1. **전문 에이전트 호출:** 전문 에이전트 하나를 호출하여 담당 분석 영역을 조사하고 분석 결과를 반환하도록 합니다. 최초에는 API 응답시간을 확인하는 API 분석 에이전트를 호출합니다.
2. **평가:** 주 에이전트는 지금까지 수집한 분석 결과를 바탕으로 현재 진단 결과와 확신도를 제시합니다. 또한 아직 호출하지 않은 전문 에이전트를 추가로 호출했을 때 기대할 수 있는 이득을 평가합니다. 확신도와 기대 이득은 각각 0에서 1 사이의 값으로 표현합니다.
3. **선택 또는 종료:** 확신도가 설정한 기준 이상이면 진단을 종료합니다. 기준에 도달하지 못했다면 효용이 가장 높은 전문 에이전트를 호출합니다. 남은 전문 에이전트의 효용이 모두 0 이하인 경우에도 진단을 종료합니다.

주 에이전트가 입력에 따라 수행할 작업을 결정하고, 전문 에이전트에 작업을 위임한 뒤 결과를 종합하는 방식은 Anthropic이 정리한 에이전트 구성 방식 중 Orchestrator-Workers[2]에 해당합니다.

전문 에이전트 $a_i$의 효용은 다음과 같이 정의합니다.

$$\
U(a_i)=\Delta Q(a_i)-\alpha C(a_i)-\beta L(a_i)\
$$

각 항의 의미는 다음과 같습니다.

- $\Delta Q(a_i)$: 전문 에이전트를 추가로 호출했을 때 기대되는 진단 정확도의 향상 정도입니다. 1에서 현재 확신도를 뺀 값에 주 에이전트가 평가한 해당 전문 에이전트의 기대 이득을 곱하여 계산합니다.
- $C(a_i)$: 전문 에이전트 호출에 따른 예상 토큰 사용량입니다. 전면 협력 구조에서 측정한 해당 전문 에이전트의 평균 토큰 사용량을 전체 다섯 전문 에이전트의 평균 토큰 사용량 합으로 나누어 정규화합니다.
- $L(a_i)$: 전문 에이전트 호출에 따른 예상 추가 지연시간입니다. 전면 협력 구조에서 측정한 해당 전문 에이전트의 평균 소요 시간을 전체 다섯 전문 에이전트의 평균 소요 시간 합으로 나누어 정규화합니다.

$\alpha$와 $\beta$는 각각 토큰 사용량과 추가 지연시간이 효용에 미치는 영향을 조절하는 가중치입니다.

실험에서는 다음 네 가지 에이전트 구조를 비교합니다.

| 구조      | 동작 방식                                                        |
| ------- | ------------------------------------------------------------ |
| 단일 에이전트 | 하나의 에이전트가 모든 진단 도구를 사용하여 전체 진단 과정을 수행합니다.                    |
| 전면 협력   | 모든 진단 요청에서 다섯 전문 에이전트를 정해진 순서대로 호출한 뒤, 주 에이전트가 분석 결과를 종합합니다. |
| 점진적 협력  | 효용 함수를 통해 다음에 호출할 전문 에이전트를 선택하고, 확신도가 종료 기준에 도달하면 진단을 종료합니다. |
| 정해진 순서  | 점진적 협력 구조와 동일한 종료 규칙을 적용하되, 전문 에이전트를 미리 정해진 순서대로 호출합니다.      |

정해진 순서 구조는 효용 함수를 활용한 전문 에이전트 선택이 진단 결과와 비용에 미치는 영향을 별도로 확인하기 위한 대조 구조입니다. 점진적 협력 구조와 전문 에이전트 선택 규칙만 다르며, 나머지 구현은 동일합니다.

### 2. 진단 서비스 설계

진단 서비스는 사용자로부터 응답 지연이 발생한 API의 HTTP 메서드와 경로를 입력받아 지연 원인을 분석하고 진단 결과를 반환합니다.

진단 대상인 주문 서비스와 진단 서비스는 별도 프로세스로 실행합니다. 실제 운영 서비스가 별도의 진단 API를 제공하지 않는 환경을 고려하여 두 서비스를 분리했습니다. 두 서비스는 Spring Boot로 구현했으며, 데이터베이스는 MySQL 8.4를 사용합니다.

[그림 1 삽입 위치: 사용자, 진단 서비스(협력 구조, 전문 에이전트, 진단 도구), 주문 서비스, MySQL 간의 관계]

전문 에이전트는 분석 영역에 따라 다음 다섯 가지로 구성합니다. 각 전문 에이전트는 자신의 분석 영역에 해당하는 진단 도구만 사용할 수 있습니다.

| 전문 에이전트  | 분석 영역                  | 진단 도구의 데이터 출처                              |
| -------- | ---------------------- | ------------------------------------------ |
| API 분석   | API 응답시간               | Spring Boot Actuator의 HTTP 요청 지표           |
| 커넥션 분석   | 커넥션 풀의 커넥션 획득 대기       | Actuator의 커넥션 풀 지표                         |
| 쿼리 분석    | SQL 실행시간 및 조회 행 수      | MySQL Performance Schema의 SQL 문장 요약 테이블[3] |
| 실행 계획 분석 | 테이블 접근 방식 및 인덱스 사용 여부  | SQL 문장 요약 테이블에 저장된 예시 SQL의 실행 계획[4]        |
| 락 분석     | 락을 기다리는 SQL 문장 및 대기 시간 | Performance Schema의 락 대기 테이블               |

진단 도구는 운영 환경에서의 안전성을 고려하여 다음 세 가지 원칙에 따라 설계했습니다.

1. **실행 계획 조회 도구는 SQL 문자열 대신 문장 식별자를 입력받습니다.** 이를 통해 에이전트가 임의로 생성한 SQL이 데이터베이스에 전달되지 않도록 합니다.
2. **실행 계획을 조회할 때 진단 대상 SQL을 실제로 실행하지 않습니다.**
3. **진단 서비스는 읽기 전용 계정을 사용하여 데이터베이스에 접속합니다.**

전문 에이전트의 분석 결과와 최종 진단 결과는 원인 범주, 대상 테이블, 대상 컬럼, 판단 근거를 포함하는 구조화된 출력(Structured Output)[5]으로 반환받습니다.

원인 범주는 연구 계획에서 정의한 다섯 가지 장애 시나리오에 정상 상태를 나타내는 `NO_PROBLEM`과 원인을 특정하지 못한 상태를 나타내는 `UNDETERMINED`를 추가하여 총 일곱 가지로 구성했습니다.

출력 형식을 고정함으로써 별도의 수동 판정 없이 스크립트를 통해 진단 성공 여부를 자동으로 평가할 수 있도록 했습니다.

구현 과정에서는 진단 도구, 협력 구조, 전문 에이전트 선택 규칙을 각각 인터페이스로 분리했습니다. 이를 통해 새로운 진단 도구나 협력 구조, 선택 규칙을 추가할 때 기존 호출부를 수정하지 않고 구현체를 추가하는 방식으로 확장할 수 있도록 설계했습니다.

실제로 정해진 순서 구조는 전문 에이전트 선택 규칙에 대한 구현체를 추가하여 구현했습니다.

LLM 요청과 진단 도구 호출을 반복하는 실행 로직은 네 가지 구조에서 공통으로 사용합니다. 또한 각 구조의 토큰 사용량과 진단 과정을 비교할 수 있도록 요청별 토큰 사용량과 진단 도구 호출 순서를 기록합니다.

## Ⅲ. 실험

### 1. 실험 환경

주문 서비스의 데이터베이스에는 주문 데이터 500만 행, 고객 데이터 50만 행, 상품 데이터 1만 행을 적재했으며, 총 11개의 API를 구현했습니다. 이 가운데 세 API에서 다음과 같은 장애 시나리오를 재현했습니다.

| 조건         | 재현 방법                                                                                                 | 기대 진단 결과                                         |
| ---------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 인덱스 미사용    | 고객별 주문 조회에 사용하는 `customer_id` 인덱스를 제거합니다.                                                             | `MISSING_INDEX`, `orders.customer_id`            |
| 비효율 SQL 조건 | 날짜별 주문 수 조회 시 `DATE(ordered_at) = ?` 조건을 사용합니다. 인덱스가 존재하지만 컬럼에 함수를 적용하여 인덱스를 통한 범위 검색이 이루어지지 않도록 합니다. | `INEFFICIENT_SQL_CONDITION`, `orders.ordered_at` |
| 락 대기       | 별도 세션에서 주문 데이터 1,000행에 대한 락을 2초씩 반복해서 획득하고 유지하는 동안 주문 상태 변경을 요청합니다.                                   | `LOCK_WAIT`, `orders`                            |
| 정상         | 인덱스가 정상적으로 적용된 고객별 주문 조회 API를 사용합니다.                                                                  | `NO_PROBLEM`                                     |

정상 조건은 장애가 발생하지 않은 API를 장애 상태로 잘못 진단하는지 확인하기 위해 포함했습니다.

실험 모델은 Claude Opus 5.5를 사용했으며, `effort`는 기본값인 `medium`으로 설정했습니다. 시스템 프롬프트에는 p99 응답시간이 500ms를 초과하면 응답 지연으로 판단하도록 기준을 명시했습니다. 단일 에이전트 구조에서는 에이전트가 직접 진단 도구를 선택할 수 있도록 별도의 호출 순서를 지정하지 않았습니다.

효용 함수의 가중치 $\alpha$와 $\beta$는 각각 0.1로 설정했으며, 진단 종료를 위한 확신도 기준은 0.8로 설정했습니다. 전문 에이전트별 예상 토큰 사용량과 예상 지연시간은 전면 협력 구조를 사전에 4회 실행하여 측정한 평균값을 사용했습니다.

실험에 사용하는 설정값은 사전 실행 결과를 확인한 뒤 확정했으며, 본 실험에서는 변경하지 않았습니다.

### 2. 측정 절차

각 실험 회차는 다음 다섯 단계로 진행했습니다.

1. 주문 서비스를 재기동하여 Actuator 지표를 초기화했습니다.
2. 데이터베이스의 실행 통계를 초기화했습니다.
3. 진단 대상 API에 동시 요청 수를 2로 설정하여 지속적으로 요청을 전송했으며, 나머지 8개 API에도 요청을 함께 전송했습니다.
4. 요청을 전송하기 시작한 시점으로부터 30초가 지난 뒤, 요청이 계속 유입되는 상태에서 진단 서비스에 진단을 요청했습니다.
5. 진단 결과, 에이전트별 토큰 사용량, 전문 에이전트 선택 과정을 기록했습니다.

실제 운영 환경에서는 서비스에 요청이 유입되는 중에 장애 진단이 이루어지며, 락 대기는 실제로 발생하고 있는 시점에 관측할 수 있습니다. 이러한 환경을 재현하기 위해 API 요청이 지속적으로 유입되는 상태에서 진단을 수행했습니다.

각 구조에 대해 조건별로 10회씩 총 40회를 측정했으며, 네 가지 구조에서 총 160회의 실험을 진행했습니다.

단일 에이전트, 점진적 협력, 전면 협력 구조는 동일한 회차 내에서 번갈아 실행했습니다. 정해진 순서 구조는 같은 날 동일한 측정 절차에 따라 별도로 실험했습니다.

정해진 순서 구조는 종료 규칙을 적용하는 것만으로 전면 협력 구조 대비 입력 토큰 사용량을 약 30% 절감했습니다. 여기에 효용 함수를 통한 전문 에이전트 선택 규칙을 적용함으로써 추가적인 비용 절감 효과를 얻을 수 있었습니다.

**넷째, 효용 함수는 장애 조건에 적합한 전문 에이전트를 우선적으로 선택했습니다.**

정상 조건에서는 10회 모두 API 분석 에이전트만 호출한 뒤 진단을 종료했습니다. 이때 점진적 협력 구조의 입력 토큰 사용량은 단일 에이전트 구조보다 약 14% 적었습니다.

**다섯째, 전체 실험 조건의 평균을 기준으로는 단일 에이전트 구조의 진단 비용이 가장 낮았습니다.**

점진적 협력 구조의 평균 입력 토큰 사용량은 단일 에이전트 구조의 약 1.6배였으며, 평균 진단 시간은 약 2.6배였습니다. 이번 실험에서 재현한 단일 원인 장애에서는 전문 에이전트 간 협력에 필요한 추가 비용만큼의 정확도 향상 효과를 확인하지 못했습니다.

### 4. 실험의 한계

이번 실험에는 다음 세 가지 한계가 있습니다.

**첫째, 실험에 포함된 장애 시나리오가 단일 원인 장애로 제한되어 있습니다.**

네 가지 구조 모두 모든 실험에서 올바른 진단 결과를 반환했으므로, 구조 간 진단 정확도의 차이를 확인하지 못했습니다. 이번 실험에서는 원인이 하나인 장애만 재현했으며, 여러 원인이 동시에 발생하는 복합 장애는 실험에 포함하지 않았습니다. 따라서 복잡한 장애 상황에서도 동일한 결과가 나타나는지는 추가 검증이 필요합니다.

**둘째, 진단 종료 여부를 판단하는 확신도와 기대 이득은 모델이 자체적으로 평가한 값입니다.**

인덱스 미사용 조건에서는 10회 중 8회가 실행 계획을 확인하지 않고, 쿼리 분석 에이전트가 확인한 조회 행 수를 근거로 진단을 종료했습니다.

해당 회차의 진단 결과는 모두 올바랐지만, 현재의 확신도 기반 종료 규칙은 장애 원인을 뒷받침하는 직접적인 증거의 확보를 보장하지 않습니다.

**셋째, 실험 모델과 가중치 조합, 표본 수가 제한적입니다.**

하나의 모델과 하나의 효용 함수 가중치 조합을 사용했으며, 각 구조에서 조건별로 10회씩 측정했습니다. 따라서 조건별 측정 결과는 제한된 표본을 기반으로 합니다.

또한 전문 에이전트별 예상 토큰 사용량과 예상 지연시간은 전면 협력 구조의 사전 실행 결과를 기반으로 산정했으므로, 해당 구조에서 전문 에이전트를 호출하는 순서가 예상 비용에 영향을 미쳤을 가능성이 있습니다.

## Ⅳ. 결론 및 향후 연구 방향

본 연구에서는 효용 함수를 통해 전문 에이전트를 선택하고, 필요한 전문 에이전트만 순차적으로 호출하는 점진적 협력 구조를 제안했습니다. 이를 검증하기 위해 장애 진단 서비스를 구현하고, 세 가지 장애 시나리오와 정상 조건에서 네 가지 에이전트 구조의 진단 정확도와 비용을 비교했습니다.

연구 질문에 대한 실험 결과는 다음과 같습니다.

점진적 협력 구조는 전면 협력 구조와 동일한 진단 정확도를 유지하면서 입력 토큰 사용량을 57%, 진단 시간을 43% 절감했습니다. 또한 동일한 종료 규칙을 사용하는 정해진 순서 구조와 비교하여 입력 토큰 사용량을 39% 절감함으로써 효용 함수에 기반한 전문 에이전트 선택의 효과를 확인했습니다.

반면 단일 에이전트 구조보다 높은 진단 정확도를 달성하지는 못했습니다. 이번 실험에서 재현한 단일 원인 장애에서는 단일 에이전트 구조가 가장 적은 비용으로 동일한 진단 정확도를 달성했습니다.

따라서 **이번 실험에서 다룬 단일 원인 장애는 단일 에이전트 구조만으로도 충분히 진단할 수 있으며, 분석 영역을 전문 에이전트로 분리해야 하는 환경에서는 점진적 협력 구조를 통해 멀티에이전트 협력에 따른 비용을 줄일 수 있습니다.**

연구는 다음 세 가지 방향으로 확장할 수 있습니다.

1. **복합 장애 재현 및 진단 대상 서비스의 규모 확장:** 두 가지 장애 원인이 동시에 발생하는 복합 장애를 재현하고, 더 많은 API를 제공하는 서비스를 대상으로 실험을 진행합니다. 이를 통해 단일 에이전트 구조의 진단 정확도가 낮아지는 조건과 멀티에이전트 구조가 효과적인 조건을 확인합니다.
2. **모델 및 가중치에 따른 성능 변화 분석:** 상대적으로 규모가 작은 모델과 다양한 효용 함수 가중치 조합을 적용하여 구조별 진단 정확도, 토큰 사용량, 진단 시간의 변화를 측정합니다.
3. **확신도 기반 종료 규칙 보완:** 모델이 자체적으로 평가한 확신도뿐만 아니라 장애 원인을 뒷받침하는 직접적인 증거의 확보 여부도 종료 조건에 포함합니다. 이를 통해 충분한 근거를 확보하지 않은 상태에서 진단을 조기에 종료하는 문제를 개선합니다.
